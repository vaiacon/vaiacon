Pretraining: Autocomplete auf Steroiden

In Modul 01 hast du gesehen: Ein LLM sagt immer nur das nächste Token voraus. Jetzt die Frage: Woher kann es das? Antwort: aus dem Pretraining — der ersten, mit Abstand teuersten Stufe der Pipeline.

Das Rezept ist brutal simpel. Man nimmt einen riesigen Textberg (Web-Crawls, Code von GitHub, Bücher, Wikipedia, Foren) und stellt dem Modell milliardenfach dieselbe Aufgabe: «Hier ist Text — sag das nächste Token voraus.» Liegt es daneben, werden die Gewichte per Gradientenverfahren einen Mini-Schritt korrigiert. Das ist konzeptionell exakt das, was ein LoRA-Trainer wie ai-toolkit macht — nur dass hier alle Parameter trainiert werden und der Datensatz das halbe Internet ist.

Die Grössenordnungen (Stand 2026)

  • Daten: Grössenordnung 10–30+ Billionen Tokens. Zum Vergleich: Eine komplette 7-TB-Filmsammlung als Text wäre ein Rundungsfehler.
  • Zeit: Wochen bis Monate Dauerbetrieb auf zehntausenden GPUs — nicht eine einzelne gemietete H100, sondern ganze Rechenzentren, bei denen inzwischen der Stromanschluss der Engpass ist, nicht die GPUs.
  • Kosten: GPT-4 wurde auf grob 80–100 Mio. $ geschätzt; Frontier-Runs 2025/26 liegen bei mehreren hundert Millionen, Tendenz Richtung Milliarden pro Modell. (Alles Schätzungen — die Firmen nennen keine exakten Zahlen.)

Das Ergebnis: das Base Model

Nach dem Pretraining hast du ein Base Model. Das ist noch kein Assistent — es ist Autocomplete auf Steroiden. Es hat aus dem Textberg Grammatik, Fakten, Code-Muster, Argumentationsstrukturen und x Sprachen aufgesogen, weil das alles hilft, das nächste Token besser zu raten. Aber es hat kein Konzept von «Frage beantworten». Gibst du ihm eine Frage, tut es das, wofür es trainiert wurde: Es setzt den Text plausibel fort. Vielleicht mit einer Antwort. Vielleicht mit fünf weiteren Fragen, wie in einem Forum-Thread. Vielleicht mit «Diese Frage wurde 47 Mal aufgerufen».

Aus der Praxis
Wenn du in Ollama Modell-Tags wie llama3.1:8b vs. llama3.1:8b-text siehst: -text ist das rohe Base Model, das andere die Assistenten-Version. Gleiche Architektur, gleiches Pretraining — der Unterschied entsteht erst in den nächsten Stufen. In der Praxis-Challenge unten probierst du genau das aus.
Warum gibt es das / wozu brauchst du das
Pretraining ist der Grund, warum du dem Modell nie beibringen musstest, was Docker, BTRFS oder ein Sampler ist — dieses Wissen wurde einmal für hunderte Millionen Dollar in die Gewichte gepresst, und du rufst es für Bruchteile eines Rappens pro Anfrage ab. Für eine kleine KI-Beratung heisst das: KMU-Kunden zahlen nie fürs Training, sondern immer nur für die Nutzung eines fertig trainierten Modells. Das Kostenargument «wir können uns KI nicht leisten» zielt fast immer auf die falsche Stufe.
Merksatz
Pretraining = Billionen Tokens, ein Ziel (nächstes Token), Monate GPU-Zeit. Ergebnis ist ein Base Model: sprachmächtig und wissensvoll, aber ein Textfortsetzer — noch kein Assistent.
Schätzfrage
Ein Frontier-Modell sieht im Pretraining etwa 15 Billionen Tokens. Angenommen, ein flott lesender Mensch schafft ~300 Tokens pro Minute, rund um die Uhr, ohne Schlaf. Wie lange bräuchte er für den Trainingsdatensatz?
2

Supervised Fine-Tuning: Aus dem Textfortsetzer wird ein Assistent

Stufe zwei ist ein Persönlichkeits-Transplantat. Beim Supervised Fine-Tuning (SFT) trainiert man das Base Model auf zehntausende bis Millionen handkuratierte Beispiel-Dialoge: eine User-Nachricht, dann eine ideale Assistenten-Antwort. Format, Ton, Struktur — alles vorgemacht. Technisch läuft weiter exakt dasselbe Verfahren wie im Pretraining (nächstes Token vorhersagen, Gewichte korrigieren), nur sind die Daten jetzt keine Web-Texte mehr, sondern Vorbild-Konversationen.

Der Effekt ist dramatisch, obwohl die Datenmenge winzig ist im Vergleich zum Pretraining: Das Modell lernt die Rolle «hilfreicher Assistent». Es beantwortet Fragen, statt sie fortzusetzen. Es strukturiert. Es hört auf zu antworten, wenn es fertig ist (Stopp-Token). Das Wissen kommt weiterhin fast komplett aus dem Pretraining — SFT gibt ihm nur ein Interface.

Aus der Praxis — LoRA-Training im Kleinen
Ein Charakter-LoRA für ein Bildmodell ist Fine-Tuning. Base Model (z.B. ein offenes 9B-Bildmodell) + eigene Beispieldaten (Charakter-Bilder mit Captions) → Gewichtsänderung → das Modell kann etwas Neues zuverlässig. LoRA ist dabei nur die sparsame Variante: Statt alle 9 Milliarden Parameter anzufassen, trainierst du kleine Zusatzmatrizen (darum passt es auf eine einzelne Miet-GPU und dauert Stunden statt Monate). Und was man dabei austariert — sagen wir bei Charakter «mira» 3000 vs. bei «lena» 4000 Steps — hat einen Namen: zu wenig Steps = Charakter sitzt nicht, zu viele = Overfitting. Grosse Labs haben beim SFT exakt dasselbe Problem, nur mit Dialogen statt Gesichtern.
Warum gibt es das / wozu brauchst du das
SFT ist der Grund, warum es überhaupt Chat-Modelle gibt — und warum dasselbe Base Model in zig Varianten existiert. Ein Anbieter tunt es auf Chat, einer auf Code, einer auf Medizin. Wenn du in Ollama ein dolphin- oder -uncensored-Modell ziehst, ist das kein «gehacktes» Modell: gleiche Base, aber ein Fine-Tuning-Datensatz, in dem Verweigerungs-Antworten schlicht nicht vorkommen. Das Verhalten steckt im Tuning, nicht in einem Filter, den jemand «abschaltet».
Merksatz
SFT = dem Base Model per Beispiel-Dialogen die Assistenten-Rolle antrainieren. Gleiches Verfahren wie Pretraining, winziger Datensatz, riesiger Verhaltens-Effekt. LoRA-Training ist dasselbe Prinzip, parametereffizient geschrumpft.
Multiple Choice
Was unterscheidet ein Charakter-LoRA-Training auf einer Miet-GPU grundsätzlich vom SFT bei einem grossen Lab?
3

RLHF: Lernen aus menschlichen Vergleichen

Nach SFT antwortet das Modell wie ein Assistent — aber oft hölzern, manchmal schädlich, manchmal schlicht am Bedürfnis vorbei. Für «gut» gibt es keine perfekte Muster-Antwort, die man vorschreiben könnte. Aber Menschen können vergleichen. Genau das nutzt RLHF (Reinforcement Learning from Human Feedback), in drei Schritten:

  • 1. Präferenzdaten: Das Modell erzeugt pro Prompt mehrere Antworten. Menschliche Bewerter wählen die bessere. Millionenfach.
  • 2. Reward Model: Aus diesen Vergleichen wird ein zweites Modell trainiert, das jede beliebige Antwort mit einer Zahl bewertet — ein automatisierter Geschmacks-Richter, der die menschlichen Präferenzen imitiert.
  • 3. Policy-Optimierung: Das eigentliche Modell generiert massenhaft Antworten, das Reward Model benotet sie, und die Gewichte werden so verschoben, dass hoch benotete Antworten wahrscheinlicher werden (klassisch mit PPO, inzwischen auch mit einfacheren Verfahren wie DPO).

Ergebnis: hilfreicher, höflicher, sicherer, besser strukturiert. Aber es gibt eine dokumentierte Nebenwirkung: Sycophancy — Schmeichelei. Menschen bevorzugen (unbewusst) Antworten, die ihnen zustimmen und ihnen ein gutes Gefühl geben. Das Reward Model lernt diese Vorliebe mit, und das Modell lernt: Zustimmung bringt Punkte. Darum neigen RLHF-Modelle dazu, dir Recht zu geben, deine Frage «grossartig» zu finden und Widerspruch in Watte zu packen — selbst wenn du falsch liegst.

RLHF ist der Schritt, der aus einem brauchbaren Tool ein Produkt gemacht hat — der Qualitätssprung von GPT-3 zu ChatGPT war zum grossen Teil genau diese Stufe. Für dich praktisch relevant ist vor allem die Nebenwirkung: Wenn Claude deine Architektur-Idee für deine selbstgebaute Web-App lobt, ist das kein Beleg, dass sie gut ist. Willst du ehrliches Feedback, musst du aktiv danach fragen («Was ist die schwächste Stelle an diesem Plan?») — damit umgehst du den antrainierten Zustimmungs-Drall.
Merksatz
RLHF: Menschen vergleichen Antworten → daraus lernt ein Reward Model → das benotet Millionen Antworten im Verstärkungslernen. Macht Modelle hilfreicher und höflicher — und als Nebenwirkung schmeichlerisch.

Constitutional AI: Warum Werte in den Gewichten stecken

Anthropic geht beim dritten Schritt einen anderen Weg: Constitutional AI. Statt (nur) Millionen menschlicher Einzelurteile gibt es einen geschriebenen Prinzipienkatalog — die Constitution. Der Trainingstrick in zwei Phasen:

  • Selbstkritik (supervised): Das Modell erzeugt eine Antwort, wird dann aufgefordert, sie selbst gegen die Prinzipien zu kritisieren («verstösst das gegen …?») und zu überarbeiten. Trainiert wird auf die überarbeiteten Versionen.
  • RLAIF: Wie RLHF, aber der Präferenz-Richter ist kein Mensch, sondern ein Modell, das anhand der Constitution entscheidet, welche von zwei Antworten prinzipientreuer ist. Reinforcement Learning from AI Feedback. Skaliert besser als Heere von menschlichen Labelern, und die Kriterien stehen schwarz auf weiss in einem Dokument statt implizit in Millionen Einzelklicks.
  • Anthropic hat die Constitution im Januar 2026 neu veröffentlicht (~80 Seiten, öffentlich einsehbar) — mit einer expliziten Prioritätenordnung: Safety vor Ethik vor Anthropic-Guidelines vor Hilfsbereitschaft. Neu erklärt sie vor allem das Warum hinter den Regeln, damit das Modell die Logik auf neue Situationen übertragen kann.

Der Punkt, der wirklich zählt: Gewichte vs. Laufzeit

Die Anthropic-Constitution kannst du als Dokument herunterladen und komplett durchlesen. Hier der technische Unterbau dazu — und ein verbreitetes Missverständnis: Die Constitution wird nicht zur Laufzeit geladen. Es gibt keinen Prozess, der bei jeder Anfrage ein PDF durchsucht und Regeln anwendet. Die Constitution ist ein Trainingsartefakt: Sie hat über Selbstkritik und RLAIF die Gewichte geformt. Wenn Claude etwas ablehnt oder abwägt, ist das dieselbe Art «Wissen» wie seine Kenntnis von Docker-Flags — eingebrannt in Zahlen, nicht nachgeschlagen in einer Regeldatei.

Davon strikt zu trennen: der System-Prompt. Der ist Laufzeit-Kontext — Text, der bei jeder Anfrage vorne in den Kontext gestellt wird (dein CLAUDE.md, Tool-Definitionen, «antworte auf Deutsch»). Er kann Verhalten steuern, aber er ändert kein einziges Gewicht, und nach der Session ist er weg.

TRAINING (einmalig)
Constitution → GewichtePrinzipien formen via Selbstkritik + RLAIF die Parameter. Permanent, für alle Nutzer gleich, ohne Neutraining unveränderbar.
≠
LAUFZEIT (pro Anfrage)
System-Prompt → KontextText vor deiner Nachricht: CLAUDE.md, Tools, Anweisungen. Steuert die Session, ändert null Gewichte, verschwindet danach.
Warum gibt es das / wozu brauchst du das
Diese Trennung beantwortet Fragen, die dir laufend begegnen: Warum kann ein Ollama-Modell «uncensored» sein? (Anderes Fine-Tuning → andere Gewichte.) Warum kannst du Claude per Prompt nicht dauerhaft «umerziehen»? (Prompt = Laufzeit, Gewichte bleiben.) Und fürs Beratungsgeschäft: Wenn ein KMU-Kunde fragt «kann man dem Ding unsere Firmenwerte beibringen?», weisst du jetzt, dass es zwei ehrliche Antworten gibt — günstig und sofort per System-Prompt (Steuerung), oder teuer per Fine-Tuning (Gewichte). Fast immer reicht Ersteres.
Merksatz
Constitutional AI = Prinzipienkatalog statt nur menschlicher Klicks; das Modell kritisiert sich im Training selbst. Die Werte landen dadurch in den Gewichten — der System-Prompt dagegen ist flüchtiger Laufzeit-Kontext.

Checkpoints

Ein Checkpoint ist ein Schnappschuss aller Gewichte zu einem Zeitpunkt im Training — bei Frontier-Modellen hunderte Gigabyte bis Terabytes. Wer schon einmal ein LoRA trainiert hat, kennt das Prinzip: alle N Steps ein .safetensors, und am Ende nimmt man nicht zwingend den letzten, sondern den besten (Stichwort Overfitting). «Ein Modell released» heisst: einen bestimmten Checkpoint zum Produkt erklären.

Distillation: Warum es Modellfamilien gibt

Grosse Modelle sind schlau, aber langsam und teuer im Betrieb. Deshalb destilliert man: Ein grosses Lehrer-Modell erzeugt massenhaft hochwertige Antworten (oder Wahrscheinlichkeitsverteilungen), ein kleines Schüler-Modell wird darauf trainiert, sie zu imitieren. Das Kleine erreicht so deutlich mehr Qualität, als es aus eigenem Pretraining derselben Grösse je hätte. Genau darum treten Modelle als Familien auf — gross/mittel/klein (bei Anthropic: Opus/Sonnet/Haiku-Klassen) — und darum können 8B-Modelle auf einem modernen Mac mit viel RAM Dinge, die vor drei Jahren nur Riesenmodelle konnten.

«Wird das Modell durch Nutzung schlauer?» — Nein.

Wichtigste Konsequenz aus allem: Nach dem Release sind die Gewichte eingefroren. Deine Chats trainieren das Modell nicht live weiter; es gibt kein «es lernt mich kennen» auf Gewichtsebene (was sich so anfühlt, ist Kontext: CLAUDE.md, Memory-Dateien — alles Laufzeit). Ein Modell-Update wie «Sonnet 4.5 → neuere Version» ist ein neues Modell: neuer Trainingslauf oder neuer Feinschliff, neuer Checkpoint, neue Modell-ID in der API. Darum kann sich Verhalten zwischen Versionen spürbar ändern — und darum pinnt man in Produktions-Setups die Modell-ID.

Warum gibt es das / wozu brauchst du das
Die Familien-Logik ist bares Geld: Für typische KMU-Automatisierungen (Mail klassifizieren, Offerten-Felder extrahieren) reicht fast immer das kleine, destillierte Modell — zehnfach günstiger, x-fach schneller. Das grosse Modell nimmst du für die harten 5% (komplexe Analysen, heikle Texte). Wer immer das Flaggschiff nutzt, verbrennt Marge; wer die Pipeline versteht, wählt pro Task die richtige Familien-Stufe.
Merksatz
Pipeline: Daten → Pretraining → SFT → RLHF/RLAIF → Evals → Release. Ein Release ist ein eingefrorener Checkpoint; kleine Modelle sind oft Destillate grosser; Nutzung ändert keine Gewichte — Updates sind neue Modelle.

Die Instruct-Version antwortet: erkennt den Satzanfang als Frage, strukturiert eine Antwort, setzt ein sauberes Ende. Gleiche Base, gleiche Parameterzahl — der komplette Unterschied ist Fine-Tuning.
