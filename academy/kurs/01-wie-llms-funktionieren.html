ABSCHNITT 1 / 6

Tokens: Die Währung der Sprachmodelle

✓ abgeschlossen

Ein LLM sieht niemals Buchstaben oder Wörter. Bevor dein Text das Modell erreicht, zerlegt ihn ein Tokenizer in Tokens — Zahlen-IDs für Textstücke. Ein Token kann ein ganzes Wort sein («und»), ein Wortteil («keit») oder ein einzelnes Zeichen. Das Modell rechnet ausschliesslich mit diesen IDs.

Die Zerlegung folgt der BPE-Idee (Byte-Pair Encoding): Man startet mit einzelnen Zeichen und verschmilzt schrittweise die häufigsten Zeichenpaare aus den Trainingsdaten zu neuen Tokens. Was oft vorkommt, wird ein eigenes Token; was selten ist, bleibt in Stücken. Deshalb ist «the» ein Token, «Erdbeere» aber typischerweise zwei bis drei (z. B. Erd+beere).

Zwei praktische Konsequenzen

  • Buchstaben zählen geht schief. Frag ein LLM, wie viele «e» in «Erdbeere» stecken: Es sieht nicht E-r-d-b-e-e-r-e, sondern etwa [Erd][beere] — zwei undurchsichtige IDs. Die Buchstaben darin sind für das Modell nicht direkt sichtbar. Gleiches Problem bei Reimen, Anagrammen, Zeichen-genauen String-Operationen.
  • Deutsch ist teurer als Englisch. Tokenizer sind auf englisch-lastigen Daten trainiert. Englisch braucht grob 1,3–1,4 Tokens pro Wort, Deutsch eher um die 2 — Komposita wie «Netzwerkspeicherkonfiguration» werden in viele Stücke gehackt. Als Grössenordnung: derselbe Inhalt kostet auf Deutsch 20–50 % mehr Tokens. Das heisst: mehr API-Kosten, schneller volles Kontextfenster.
✦ Tokenizer-Demo

Tipp Text ein — er wird live in Token-Chips zerlegt. Ehrlichkeitshinweis: Das ist eine Näherung mit einer kleinen Subword-Liste, kein echter BPE-Tokenizer (der hätte ~100'000 gelernte Merges). Die Grössenordnung stimmt aber.

Aus deiner Welt Wenn du Claude Code auf Deutsch bedienst, bezahlst du den Deutsch-Aufschlag bei jedem Turn — dein Prompt und die ganze bisherige Session laufen als Tokens durch. Bei Ollama lokal kostet es kein Geld, aber Kontextplatz und Rechenzeit: gleiche Mechanik, gleicher Tokenizer-Schritt vor dem Modell.
Warum gibt es das? Zeichen einzeln wären zu viele Schritte (jedes «e» ein Rechendurchlauf), ganze Wörter als Vokabular wären Millionen Einträge plus «unbekanntes Wort»-Problem. Subword-Tokens sind der Kompromiss: ~50'000–200'000 Vokabular-Einträge decken jeden möglichen Text ab — auch Tippfehler, Code und «Sonarr». Du brauchst das Wissen konkret beim Kosten-Abschätzen von API-Calls und beim Verstehen, warum Kontextfenster in Tokens (nicht Wörtern) gemessen werden.
Merksatz Ein LLM liest keine Buchstaben, sondern Token-IDs. Alles, was zeichen-genau ist (zählen, buchstabieren), ist für das Modell strukturell schwer — und Deutsch kostet spürbar mehr Tokens als Englisch.
ABSCHNITT 2 / 6

Next-Token-Prediction: Das Modell tut nur eines

✓ abgeschlossen

Hier ist die vielleicht wichtigste Einsicht des ganzen Kurses: Ein LLM macht zur Laufzeit genau eine Operation. Es nimmt die bisherige Token-Folge und berechnet eine Wahrscheinlichkeitsverteilung über das nächste Token — für jedes der ~100'000 Vokabular-Tokens eine Zahl. Dann wird eines gewählt (per Sampling), angehängt, und das Ganze läuft erneut. Token für Token, bis ein Stopp-Token kommt.

Es gibt keinen zweiten Modus. Wenn Claude dir ein Bash-Script schreibt: Next-Token-Prediction. Wenn es «nachdenkt» (Extended Thinking): Next-Token-Prediction, nur in einen Denkblock hinein. Wenn es sich entschuldigt: dito. Antworten, Argumente, Code-Struktur — alles emergiert aus dieser einen Operation, weil das Modell im Training gelernt hat, welche Fortsetzungen in welchem Kontext plausibel sind.

Die Sampler-Regler, die du von ComfyUI und der API kennst (Temperature, Top-p), setzen genau hier an: Sie steuern, wie aus der Verteilung gewählt wird — gierig immer das Top-Token, oder auch mal ein unwahrscheinlicheres.

✦ Next-Token-Visualisierung

So sieht die Welt aus Modellsicht aus: ein angefangener Satz, eine Verteilung über Fortsetzungen. Klick auf einen Balken, um das Token zu wählen — dann kommt die nächste Verteilung. (Wahrscheinlichkeiten hier handgebaut zur Illustration, aber realistisch geformt.)

Aus deiner Welt Wenn Ollama auf deinem Mac Text «streamt», siehst du diese Schleife live: Jedes aufpoppende Textstück ist ein frisch gesampeltes Token. Und dass die Antwort bei gleichem Prompt zweimal anders ausfällt, liegt nicht an «Laune» — sondern daran, dass bei Temperature > 0 aus der Verteilung gezogen wird statt immer das Maximum zu nehmen.
Warum gibt es das? Next-Token-Prediction ist das einzige Trainingsziel, für das es praktisch unbegrenzt Trainingsdaten gibt: jeder existierende Text ist automatisch ein Übungsbeispiel («verdecke das nächste Wort, rate es»). Kein Mensch musste Millionen Beispiele labeln. Für dich ist das der Schlüssel, um Modellverhalten zu debuggen: Bei jeder seltsamen Antwort lautet die richtige Frage nicht «warum lügt es?», sondern «warum war diese Fortsetzung aus Sicht der Trainingsdaten plausibel?».
Merksatz Ein LLM berechnet immer nur die Wahrscheinlichkeitsverteilung für das nächste Token. Alles andere — Antworten, Code, «Denken» — ist diese eine Operation in Schleife.
ABSCHNITT 3 / 6

Gewichte vs. Kontext: Zwei völlig verschiedene Gedächtnisse

✓ abgeschlossen

Woher «weiss» das Modell überhaupt, welche Fortsetzung plausibel ist? Aus zwei Quellen, die man sauber trennen muss:

Die Gewichte sind Milliarden Parameter, die im Training (Monate, riesige GPU-Cluster) eingestellt wurden. Zur Laufzeit werden sie nie verändert — nur gelesen. Der Kontext ist das flüchtige Arbeitsgedächtnis: alles, was in dieser einen Anfrage als Token-Folge vorliegt.

Daraus folgt eine Kette von Konsequenzen, die viele überrascht:

  • Das Modell läuft serverseitig. Wenn du mit Claude chattest, gehen deine Tokens an Anthropic-Server; dort läuft die Vorhersage-Schleife gegen die eingefrorenen Gewichte. Auf deinem Mac läuft nur die Anzeige. (Bei Ollama läuft dieselbe Maschinerie lokal — deshalb liegen dort die Gewichte als Datei auf deiner SSD.)
  • Dein Prompt ändert das Modell nicht. Egal was du schreibst — kein Bit der Gewichte bewegt sich. Wenn Claude mitten im Gespräch etwas «lernt» (z. B. dass dein Sonarr KEIN Docker-Container ist), lebt dieses Wissen ausschliesslich im Kontext dieser Session.
  • Deshalb erinnert sich Claude nach Session-Ende an nichts. Der Kontext wird verworfen; die Gewichte waren nie anders. Neues Gespräch = leeres Arbeitsgedächtnis.
  • «Gedächtnis» muss man aussenrum bauen: Text speichern und beim nächsten Mal wieder in den Kontext laden. Mehr nicht — aber genau das machen alle Memory-Systeme.
Aus deiner Welt Die MEMORY.md- und Memory-Dateien von Claude Code (unter ~/.claude/projects/…/memory/) sind exakt so ein externes Gedächtnis: Claude schreibt am Session-Ende Text in Dateien, und beim nächsten Start wird dieser Text wieder in den Kontext geladen. Ein Memory-MCP-Server macht dasselbe mit einem Wissensgraphen. Claude «erinnert» sich nicht — es liest nach. Der Unterschied ist unsichtbar, solange die Dateien da sind, und brutal sichtbar, wenn nicht.
Warum gibt es diese Trennung? Training kostet Millionen und dauert Monate — das kann nicht pro Nutzer passieren. Ein eingefrorenes Modell, das über den Kontext gesteuert wird, ist der Trick, der LLMs als Massenprodukt möglich macht: ein Gewichtssatz, Millionen gleichzeitige Nutzer, jeder mit eigenem Kontext. Für dich praktisch: Alles, was Claude über dein NAS-Setup «wissen» soll, musst du in den Kontext bringen (CLAUDE.md, Memory, MCP) — es in die Gewichte zu bekommen hiesse Fine-Tuning, ein völlig anderes Kaliber (Modul 02).
Merksatz Gewichte = eingefrorenes Trainings-Wissen, ändern sich zur Laufzeit nie. Kontext = flüchtiges Arbeitsgedächtnis pro Anfrage. «Lernen im Chat» ist immer nur Kontext — darum braucht Erinnerung externe Dateien.

ABSCHNITT 4 / 6

Halluzinationen: Plausibel ≠ wahr

✓ abgeschlossen

Jetzt kannst du Halluzinationen aus den Bausteinen herleiten, statt sie als mysteriösen Bug zu sehen. Das Modell wählt die plausibelste Fortsetzung — gemessen an Mustern in den Trainingsdaten. Es gibt keinen eingebauten Wahrheits-Check: keine Datenbank-Abfrage, kein Nachschlagen, kein «weiss ich nicht»-Signal aus der Architektur heraus. Wenn die wahre Antwort in den Gewichten schwach oder gar nicht vertreten ist, gewinnt einfach die plausibel klingende Fortsetzung.

Und weil das Modell im Training fast nur selbstsichere, flüssige Texte gesehen hat, kommt auch die erfundene Antwort im selben souveränen Ton. Konfidenz im Tonfall sagt nichts über Korrektheit — der Ton ist Stil, nicht Signal.

Wann es besonders häufig passiert

  • Seltene Fakten: Je seltener etwas in den Trainingsdaten vorkam, desto schwächer die Spur in den Gewichten. Über Docker allgemein: massenhaft Daten. Über die API-Eigenheiten von Bazarr in einer bestimmten Version: fast nichts.
  • Exakte Zahlen, URLs, Zitate, Versionsnummern: Hier gibt es genau eine richtige Fortsetzung und tausende plausible. docs.example.com/api/v2/auth sieht korrekt aus — ob die Seite existiert, kann das Modell nicht prüfen.
  • Erfundene Prämissen: Fragst du «Warum nutzt Sonarr Port 8990?», spielt das Modell oft mit, statt die Prämisse zu korrigieren — die Frage klingt ja, als wäre sie wahr.
  • Wissens-Cutoff: Alles nach dem Trainingsdaten-Stichtag existiert in den Gewichten schlicht nicht — gefragt danach, wird plausibel extrapoliert.
Aus deiner Welt Genau deshalb kann Claude bei Konfigfragen zu einem Heim-NAS halluzinieren: Synology-DSM-Pfade, Sonarr-API-Felder oder SABnzbd-Kategorien-Details sind Nischenwissen mit dünner Trainingsdaten-Abdeckung. Ein erfundenes /usr/syno/etc/… klingt völlig plausibel. Das Gegenmittel kannst du selbst bauen: Eine CLAUDE.md pinnt die verifizierten Ports, Keys und Pfade in den Kontext (am besten mit Vermerk «live verifiziert» plus Datum) — Kontext schlägt schwaches Gewichts-Wissen. Und Claude Code kann per curl/ssh nachschauen statt raten: Tool-Zugriff ist der andere Halluzinations-Killer.
Wozu brauchst du das? Damit du weisst, wann du prüfen musst — für dich und für alle, denen du KI-Nutzung beibringst. Faustregel fürs Schulen von KMU: LLM-Aussagen über breites Allgemeinwissen sind meist solide; alles Exakte (Zahlen, Rechtsartikel, URLs, Preise, firmenspezifische Details) gehört verifiziert oder per RAG/Tools mit echten Quellen unterfüttert. Wer das versteht, setzt LLMs dort ein, wo sie stark sind — statt ihnen entweder blind zu vertrauen oder sie ganz abzulehnen.
Merksatz Halluzination ist kein Bug im Code, sondern die Architektur selbst: plausibelste ≠ wahre Fortsetzung, und ein Wahrheits-Check ist nicht eingebaut. Höchste Gefahr bei seltenen Fakten und allem Exakten.
ABSCHNITT 5 / 6

Das Kontextfenster: Warum das Arbeitsgedächtnis begrenzt ist

✓ abgeschlossen

Der Kontext ist nicht beliebig gross. Typische Fenster 2026: ~200'000 Tokens bei Claude-Modellen (teils bis 1 Mio.), 1–2 Mio. bei einzelnen Frontier-Modellen, oft 8k–128k bei lokalen Ollama-Modellen. 200k Tokens klingen nach viel — eine lange Claude-Code-Session mit Datei-Inhalten, Tool-Ausgaben und Logs frisst das erstaunlich schnell.

Warum überhaupt eine Grenze? Zwei technische Gründe:

  • Attention skaliert quadratisch. Der Kern-Mechanismus (Attention) vergleicht beim Verarbeiten jedes Token mit jedem anderen. Doppelt so viel Kontext ⇒ viermal so viele Vergleiche. Zehnmal so viel ⇒ hundertmal.
  • KV-Cache frisst Speicher. Damit nicht bei jedem neuen Token alles neu gerechnet wird, hält das Modell pro Token Zwischenergebnisse (Key/Value-Vektoren) im GPU-Speicher. Der wächst linear mit dem Kontext und ist bei langen Fenstern schnell mehrere Gigabyte — pro laufender Anfrage.
✦ Simulation: Was Kontextlänge kostet

Zieh den Regler. Attention-Aufwand relativ zu 8k-Kontext; KV-Cache als Grössenordnung für ein 8B-Modell à la Ollama (~130 KB/Token, FP16) — auf einem modernen Mac geht das vom Unified Memory ab.

Was passiert, wenn das Fenster voll ist?

Irgendwas muss weichen. Zwei Standard-Strategien:

  • Abschneiden: Die ältesten Nachrichten fliegen raus. Billig, aber das Modell «vergisst» abrupt den Session-Anfang.
  • Kompaktierung: Das Modell fasst den bisherigen Verlauf zusammen und ersetzt ihn durch die Zusammenfassung. Genau das macht Claude Code, wenn es «Compacting conversation…» meldet. Danach existiert vom Anfang nur noch das Kondensat — Details (exakte Fehlermeldungen, verworfene Ansätze, ein Pfad aus Message 3) können dabei verloren gehen.
Aus deiner Welt Praktische Folgen für lange Claude-Code-Sessions: (1) Nach einer Kompaktierung kann Claude Details von vorhin «vergessen» haben — wichtige Entscheide besser in eine Datei oder Memory schreiben lassen, das überlebt. (2) Grosse Datei-Dumps und Log-Fluten füllen das Fenster sinnlos — gezielt lesen lassen statt cat über alles. (3) Für einen sauberen Themenwechsel ist eine frische Session oft besser als eine zugemüllte alte: leerer Kontext, volle Aufmerksamkeit.
Warum gibt es das? Das Kontextfenster ist der Preis-Leistungs-Hebel der ganzen LLM-Ökonomie: Grössere Fenster = quadratisch mehr Rechenzeit + linear mehr GPU-Speicher = teurere Anfragen. Wer versteht, dass Kontext eine knappe Ressource ist, arbeitet automatisch besser mit LLMs: relevante Infos rein, Ballast draussen. Das ist die halbe Miete von gutem Prompting (Modul 03) und der Grund, warum RAG existiert (Modul 04) — statt alles ins Fenster zu stopfen, holt man nur das Relevante.
Merksatz Kontext ist knapp, weil Attention quadratisch und KV-Cache linear kosten. Ist das Fenster voll, wird abgeschnitten oder kompaktiert — was nicht extern gesichert ist, kann dann weg sein.

Was ein Prompt wirklich tut

✓ abgeschlossen

Mit den Bausteinen von oben kannst du jetzt präzise sagen, was ein Prompt ist — und was nicht. Ein Prompt programmiert nichts um und ändert keine Gewichte. Er ist Kontext, und Kontext konditioniert die Wahrscheinlichkeitsverteilung: Dieselben eingefrorenen Gewichte produzieren völlig andere Verteilungen, je nachdem, welche Tokens davor stehen.

Nach «Das Rezept für Zopf beginnt mit» ist «Mehl» hochwahrscheinlich. Nach «#!/bin/bash» sind es Shell-Kommandos. Der Prompt verschiebt die Wahrscheinlichkeitsmasse — nichts anderes tun auch die raffinierteren Steuer-Instrumente:

  • System-Prompt: Tokens, die vor allem anderen im Kontext stehen und damit alles Nachfolgende konditionieren. Deine CLAUDE.md wird genau so eingespeist — deshalb «weiss» Claude Code deine NAS-IP: Sie steht buchstäblich am Anfang des Kontexts jeder Session.
  • Beispiele (Few-Shot): Zeigst du zwei Beispiele im Wunschformat, ist die wahrscheinlichste Fortsetzung ein drittes im selben Format. Muster fortsetzen ist das, was Next-Token-Prediction am besten kann.
  • Rollen («Du bist ein erfahrener DevOps-Engineer»): Verschieben die Verteilung in die Textregionen, wo solche Sätze in den Trainingsdaten standen — hin zu Fachvokabular und typischen Experten-Formulierungen. Kein Schalter, der «Expertenwissen aktiviert», sondern eine statistische Weiche.

Warum gute Prompts wirken, ist damit entzaubert: Sie machen die gewünschte Fortsetzung zur wahrscheinlichsten. Präzise Anforderungen, Beispiele und relevanter Kontext engen den Raum plausibler Fortsetzungen so ein, dass fast nur noch das Richtige übrig bleibt. Vage Prompts lassen dem Modell einen riesigen Plausibilitätsraum — und dann bekommst du irgendeine generische Mitte. Das Handwerk dazu kommt in Modul 03.

Aus deiner Welt Wer Claude Code ernsthaft nutzt, betreibt schnell professionelles Kontext-Engineering, ohne es so zu nennen: CLAUDE.md (System-Kontext mit verifizierten Fakten), Memory-Dateien (persistierter Kontext), MCP-Server (holen frischen Kontext zur Laufzeit rein). Wenn Claude dann selten über deine Ports halluziniert, ist das kein Zufall — du hast die Verteilung mit Fakten konditioniert.
Wozu brauchst du das? Weil «Prompt = Konditionierung» das mentale Modell ist, das schlechtes von gutem LLM-Arbeiten trennt. Wer denkt, er «befiehlt» einer Person, wundert sich über Ungehorsam. Wer weiss, dass er eine Verteilung formt, fragt automatisch: Welche Tokens im Kontext machen mein Wunschergebnis wahrscheinlich — und welche fehlen noch? Das ist auch der Kern jedes guten Prompting-Workshops in einem Satz.
Merksatz Ein Prompt ändert nie das Modell — er konditioniert die Verteilung über Fortsetzungen. System-Prompt, Beispiele und Rollen sind nur verschiedene Wege, Wahrscheinlichkeitsmasse dorthin zu schieben, wo du sie haben willst.

Praxis-Challenge: Gewichte und Kontextfenster anfassen

Du schaust dir an deinem eigenen Ollama-Setup an, wo Gewichte und Kontextfenster konkret stehen. Im Terminal:

# 1) Welche Modelle (= Gewichtsdateien!) liegen lokal?
ollama list

# 2) Steckbrief eines Modells — nimm eines aus deiner Liste:
ollama show <modellname>

# 3) Wo liegen die Gewichte physisch auf deiner SSD?
du -sh ~/.ollama/models

Das solltest du sehen:

  • Bei ollama show: eine Zeile parameters (z. B. «8.0B» — das sind die Milliarden eingefrorenen Gewichte aus Abschnitt 3) und eine Zeile context length (das Kontextfenster aus Abschnitt 5, oft 4096–131072).
  • Bei du -sh: mehrere GB — das ist das Modell. Kein Wissen ausserhalb dieser Datei plus dem, was du pro Anfrage in den Kontext gibst.

Bonus-Verständnis-Check: Starte ollama run <modell>, erzähl ihm deinen Namen, beende mit /bye, starte neu und frag nach deinem Namen. Du weisst jetzt genau, warum er weg ist — und warum Memory-Dateien in Claude Code dieses Problem lösen.
